# Benchmark: 100k and 1M synthetic records, load, queries and partition evolution (dev, 2026-11-11)

**What this is:** the Week 10 benchmark runs (work package G, acceptance test 12; ADR 0034):
scale 18 (about 100k rows, sections 1 and 2) and scale 180 (about 1M rows, section 3). Every
number below was measured on AWS on 2026-11-11. The datasets are synthetic (seed 42), and the tenants `tenant_alder` and `tenant_birch` are fictional. These are reproducible
starting workloads, not a claim about any real organisation's volume.

**Isolation:** the run used its own namespace end to end:
- a local database `procurelake_bench`;
- Bronze `bronze/postgres_bench/`;
- the Glue databases `procurelake_dev_bench_silver` and `procurelake_dev_bench_gold` under
  `s3://<lake>/bench/`.

The dev Silver and Gold, the CDC pipeline and the tenant products were not touched.

**Reproduce:** `make bench-db`, `bench-snapshot`, `bench-silver-run`, `bench-dbt-build`, then
`bench-queries LABEL=…`. Partition evolution: `bench-partition-evolve [REWRITE=true]`. Compare
runs with `bench-compare BEFORE=… AFTER=…`. Raw records go to `build/evidence/` (not committed);
Glue job reports go to the artifacts bucket.

## 2. Analytical queries and partition evolution

**How the queries ran:**
- 7 queries from `configs/benchmarks/athena_queries.yaml`, 5 sequential runs each, on the
  engineering workgroup as the data engineer.
- Athena result reuse was off; the runner refuses a reused result.
- Every answer was identical across repeats and across the three layouts. `bench-compare` fails
  on any difference.

**Three layouts of the same bench Silver:**
1. **tenant only:** the Silver job's spec, `tenant_id` identity (2 data files per table). The
   evidence label is `unpartitioned`, which is a misnomer: the table *was* partitioned by tenant.
2. **evolved, not rewritten:** `ALTER TABLE … ADD PARTITION FIELD months(invoice_date)` on
   `silver_invoices`, and `months(awarded_at)` on `silver_awards`. The job took 78 s and 157
   DPU-s.
3. **evolved and rewritten:** `rewrite_data_files` with `rewrite-all`. The job took 114 s and
   229 DPU-s.

**Layout (from each table's `files` metadata table, data files only):**

| Table | Layout 1 | Layout 2 | Layout 3 |
|---|---|---|---|
| `silver_invoices` | 2 files, spec 0, 6.92 MB | 2 files, spec 0 (unchanged) | 64 files, spec 1, 7.60 MB |
| `silver_awards` | 2 files, spec 0, 1.62 MB | 2 files, spec 0 (unchanged) | 62 files, spec 1, 2.20 MB |

- **Adding the field was metadata-only, as Iceberg documents.** No file moved, and the new spec
  became `tenant_id, months(…)`.
- **The rewrite moved every file to spec 1.** It rewrote 2 files into 64 and 62, with 0 failures.
  Storage grew 10% and 36%: more, smaller Parquet files, each with its own footer and less
  compression.

**Median bytes scanned and engine time (5 runs):**

| Query | Prunes on | Bytes, layout 1 | Bytes, layout 2 | Bytes, layout 3 | Engine ms (1 / 2 / 3) |
|---|---|---|---|---|---|
| `invoices_one_quarter_silver` | invoice_date | 271,233 | 271,233 | **24,722 (−91%)** | 593 / 718 / 644 |
| `awards_one_month_silver` | awarded_at | 121,888 | 121,888 | **4,122 (−97%)** | 624 / 592 / 635 |
| `invoices_all_silver` (control, full scan) | n/a | 200,138 | 200,138 | 209,404 (+5%) | 550 / 594 / 689 |
| `invoices_one_quarter_gold` | n/a (Gold unchanged) | 269,778 | 269,778 | 269,778 | 619 / 651 / 647 |
| `supplier_awarded_value_top20` | n/a | 94,935 | 94,935 | 94,935 | 612 / 591 / 523 |
| `agency_monthly_actual_spend` | n/a | 142,483 | 142,483 | 142,483 | 614 / 583 / 611 |
| `monthly_awarded_value_from_fact` | n/a | 56,156 | 56,156 | 56,156 | 525 / 557 / 564 |

**What this shows:**
- **Athena prunes Iceberg month partitions from a plain filter on the source column.** The
  quarter query read 9% of the bytes and the month query 3%. The Athena documentation does not
  say this outright (ADR 0034); it is measured here.
- **Evolution without a rewrite changes nothing for existing data.** Old files keep the old
  spec, and Athena still reads them all. Only new writes and rewritten files are pruned.
- **At this volume, pruning saves bytes but not time.** Every query ran in 0.5–0.7 s of engine
  time whatever the layout: fixed planning and scheduling cost dominates a few-megabyte table.
  Byte savings cost nothing either, because every query is below Athena's 10 MB billing minimum.
- **The full scan paid for the smaller files:** +5% bytes and the slowest median of the three
  (689 ms). The 1M run will show whether either effect grows.

## 3. The 1M run (scale 180)

**Setup:**
- 1,042,769 rows, fingerprint `b363db11…`:
  - suppliers 18,900;
  - solicitations 117,000;
  - awards 115,003;
  - purchase orders 276,419;
  - invoices 515,432;
  - agencies 13, tenants 2.
- The bench tables were dropped first, so this is a first load into the tenant-only layout,
  like the 100k baseline.
- Snapshot batch `20261111T161553Z-7c9f837f`: every table reconciled.

**Load:**

| Stage | 100k | 1M | Scaling |
|---|---|---|---|
| Snapshot to Bronze | 12 s | 98 s | 8.2× |
| Bronze → Silver (Glue G.1X × 2) | 511 s, 1,022 DPU-s (≈ $0.12) | 3,242 s, 6,485 DPU-s (≈ $0.79) | 6.3× |
| Silver → Gold (dbt, 75 nodes, all pass) | 38.9 s, 16.2 MB scanned | 41.5 s, 166 MB scanned | 1.07× |

- **The first 1M Silver attempt hit the job's 30-minute timeout** (3,603 DPU-s ≈ $0.44). It
  had finished only `agencies` and `awards`. The bench job's timeout is now 120 minutes; dev's
  is unchanged. The two committed tables were dropped before the measured run.
- **Silver time per table at 1M:**

| Table | Rows | Time | Rows/s |
|---|---|---|---|
| awards | 115,003 | 3.8 min | ~500 |
| **invoices** | **515,432** | **35.0 min** | **~245** |
| purchase_orders | 276,419 | 8.4 min | ~550 |
| solicitations | 117,000 | 4.6 min | ~425 |
| suppliers | 18,900 | 0.5 min | n/a |

- **Invoices is the bottleneck** at both scales (204 s at 100k, against 62 s for purchase
  orders with half the rows). It took 65% of the 1M run.
- **The cause was validation, now fixed and measured** (section 5).
- **Gold time barely moved with 10× the data:** Athena's per-query overhead dominates at this
  size.

**Partition evolution at 1M:**
- Adding the fields: 98 s, 197 DPU-s. No file moved, and the spec went from `tenant_id` to
  `tenant_id, months(…)`.
- The rewrite: 126 s, 252 DPU-s.
  - `silver_invoices`: 2 files (71.5 MB) became 64 files (70.6 MB, −1%).
  - `silver_awards`: 2 files (16.1 MB) became 64 files (17.4 MB, +8%).

**Median bytes scanned and engine time (5 runs; identical answers across the three layouts):**

| Query | Prunes on | Bytes, tenant only | Bytes, evolved | Bytes, rewritten | Engine ms (1 / 2 / 3) |
|---|---|---|---|---|---|
| `invoices_one_quarter_silver` | invoice_date | 2,600,139 | 2,600,139 | **236,437 (−91%)** | 703 / 745 / 704 |
| `awards_one_month_silver` | awarded_at | 1,230,068 | 1,230,068 | **39,392 (−97%)** | 657 / 701 / 619 |
| `invoices_all_silver` (control) | n/a | 1,974,297 | 1,974,297 | 1,950,558 (−1%) | 729 / 763 / 847 |
| `invoices_one_quarter_gold` | n/a | 2,625,644 | 2,625,644 | 2,625,644 | 698 / 1,057 / 715 |
| `supplier_awarded_value_top20` | n/a | 963,996 | 963,996 | 963,996 | 653 / 920 / 814 |
| `agency_monthly_actual_spend` | n/a | 1,304,327 | 1,304,327 | 1,304,327 | 704 / 755 / 706 |
| `monthly_awarded_value_from_fact` | n/a | 558,697 | 558,697 | 558,697 | 645 / 1,313 / 607 |

**What 1M adds:**
- **Pruning ratios held exactly** (−91% and −97% of bytes).
- **Engine time is still flat at 0.6–0.85 s.** Single runs vary more than the layouts differ: the
  maximums reach 2.6 s, and the same unchanged Gold query has medians from 698 to 1,057 ms
  across passes.
- **Storage stopped growing with the rewrite.** At 1M the monthly files are about 1.1 MB
  (invoices) and 270 KB (awards), large enough that compression no longer suffers.
- **Nothing billable changed.** The largest Silver scan is 2.6 MB, still under Athena's 10 MB
  per-query minimum.

## 4. Conclusion for open question 13

Up to about 1M rows:
- **Time partitioning of Silver saves neither time nor money.** Scans stay below the billing
  minimum, and latency is fixed overhead.
- **It does cut bytes read on date-filtered queries by 91–97%.** That would matter once those
  scans pass the 10 MB minimum. At the measured rate (2.6 MB per quarter of invoices at 1M),
  that is roughly 4× the 1M volume, *extrapolated, not measured*.
- **Recommendation:** keep `tenant_id`-only partitioning for Silver now. Revisit `months()` on
  invoices and awards when a date-filtered Silver scan exceeds 10 MB. It is a metadata-only
  change plus one rewrite, measured here at about 2 minutes for 1M rows.

## 5. Silver validation fix, before and after (1M, same batch)

**Change** (commit `8c091d8`):
- Presence ("the source supplied a non-null value") now comes from one `from_json` of the line
  into `map<string,string>`. Before, `get_json_object` ran up to twice per column.
- The checked rows are materialised once (`localCheckpoint`) before the valid/rejected split.
  Before, the parse and every check ran once per branch.

The validation rules are unchanged. CI's Spark suite passed, including new cases for an object
and an array in a typed column.

**Same snapshot batch** (`20261111T161553Z-7c9f837f`), bench tables dropped first, same Glue
job and size (G.1X × 2):
